How the joins work

One row per docket entry, both cases, joined to its held file, its text rendition and its tier: v_lookup = trial_dockets (495) ∪ appeal_dockets (20) ∪ register_tail (9) = 524 rows. The lookup keys the task asks for all resolve: case_number ↔ docket ↔ ra_pdf_page ↔ sha256 ↔ quote ↔ extraction_method ↔ tier. quotes holds 9 verbatim sentences with their source file and sha256; texts holds 491 text renditions with method.

Memory and size limits — stated, not hidden

  • What is downloaded: data/query.sqlite 663,552 B + sql-wasm.wasm 654,690 B + sql-wasm.js 49,857 B = 1,368,099 B (1.30 MiB), all from this site.
  • Memory: the whole database is materialised in WebAssembly memory, so the tab needs roughly 3–5× the file size (≈3–4 MiB) plus results. A phone with a few hundred MB free runs it comfortably.
  • Results: the result table renders at most 500 rows; aggregate counts are printed in full. Add your own LIMIT for wide scans.
  • Not included: the PDF bytes (the site publishes none) and the 491 text bodies (they are on /texts and in data/texts.json — the database holds their paths and hashes).
  • Read-only: no writes, no server round-trip, no query logging.

The canonical machine file remains /data/ssot.sqlite (696,320 B, sha256 f28d4b6d24c6f861…). query.sqlite is derived from it plus data/tier_map.json and the trace citations; it adds tiers, quotes and the v_lookup view and changes nothing it copies.
